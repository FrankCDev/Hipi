# Rust 测试、基准与验收规范

## 1. 状态与适用范围

本文件规定后续 Rust 模块的验证方法，不是测试通过报告。当前处于规划阶段；没有本计划的新 Rust Agent 模块、测试执行结果或性能实测可据此宣布交付。仓库已有的其他 Rust 组件不代表新内核通过验收。模块交付使用 [模块验收模板](MODULE-ACCEPTANCE-TEMPLATE.md)，并遵守 [VISION.md](../../VISION.md) 和仓库 `AGENTS.md`。

执行检查前遵守 [资源安全规范](RESOURCE-SAFETY.md)：同一时刻一个重任务，分别限制编译并发和测试并发，按实测余量设置时间、内存与磁盘预算。下面的命令不是绕过这些执行限制的许可。

行为和性能参考固定为 TypeScript 提交 `1402973a9dbe8c627341e04c9744c54953e285ca`。不要将移动的 `main` 当作基线。开发在 `dot/develop`；本规范不授权安装依赖、运行测试、提交或推送。后续执行须符合当次授权及仓库规则。

每个模块实现前冻结：支持范围、输入输出、不变量、错误与取消语义、资源上限、平台/feature 矩阵、验收用例及性能预算。预算要有工作负载和理由；不能看到结果后悄悄放宽。设计调整需记录原因、影响并重新评审。

## 2. 测试组织：以行为和风险决定层次

测试金字塔表示多数检查应快速、局部、确定，少量检查覆盖真实边界和组合路径；不规定测试数量或覆盖率配额。

- 单元测试：状态转换、增量解析、错误分类、资源计数等纯逻辑。断言公开行为或设计不变量，不绑定内部调用次数和私有布局。
- 集成测试：真实 HTTP 客户端/本地服务器、临时目录、真实子进程与终端适配器。穿过生产路径，验证超时、取消、错误、清理的组合行为。
- 差分测试：同一夹具分别进入固定 TypeScript 版本与 Rust 公开入口，比较可观察结果、事件顺序、错误类别和副作用。
- 端到端测试：少量完整会话，从输入到工具执行、会话落盘和关闭，默认使用本地 faux/mock provider，不调用付费模型。

每个用例写清“输入/故障 → 预期行为 → 如何观察”。例如，消费者暂停读取，发送超过设计队列上限的事件；观察队列高水位不超过上限，并在消费者取消后观察请求任务退出、连接关闭。仅证明 `cancel()` 返回不算验证清理。

避免为每层建立 mock 后只验证 mock；确定性时钟、故障注入和假模型用于控制外部条件，不能替代实际协议、文件和进程边界。禁止用 `assert!(true)`、直接比较硬编码同值等断言充数；固定预期值应由契约/独立夹具推导，实际值必须来自被测代码输出。覆盖率仅用于找漏测路径，不能替代失败路径和不变量验证。

纯类型和薄包装允许由所属模块或使用方场景覆盖，注明具体用例与基准，不为每个文件制造独立 harness。序列化、错误转译、转发、分配与取消仍需被覆盖。

## 3. 必选风险场景（按模块适用性选择并说明）

### 3.1 HTTP、流与模型协议

使用绑定回环地址、随机可用端口的真实本地 HTTP 服务，驱动生产 HTTP 客户端。解析器单元测试精确控制字节切分，网络集成测试不能假定一次 write 对应一次 read。

- UTF-8 多字节字符在任意字节边界分片；SSE 行和事件边界分片、CRLF、空行、多条事件合并、注释、空 payload 与未知字段。按支持的协议契约定义合法/非法结果。
- 多工具交错输出：按调用 ID 关联，增量 JSON 在字符串、转义和嵌套结构处分片；空参数、重复/缺失 ID、无效最终 JSON、超长参数、未知工具。不允许把两个工具的参数拼在一起。
- 正常终止标志、缺失终止标志、半个 UTF-8/JSON/SSE 时 EOF、HTTP body 截断、服务端断开。禁止把截断结果误报成完整成功。
- 慢消费者、暂停消费者、消费者直接 drop、队列满时取消、连接前/响应头后/处理中取消；断言有界缓冲、无遗留任务、取消后的事件规则和句柄释放。
- 超时、429/5xx、无效响应、连接失败与重试耗尽；验证错误分类、重试次数上限、退避及取消退避。注入时钟验证计时策略，另用真实计时的有界集成测试验证连接/任务生命周期。
- 输出已部分交付或工具已产生副作用时，不得隐式重试造成重复。是否可重试、如何去重及“恰好一次”承诺必须有明确契约，不能仅凭测试未观察到重复就作保证。

API Key、Base URL、model ID 的校验和协议适配分别验证；配置形式相同不等于协议兼容。实际模型 smoke test 若另获授权，仅验证连接及协议能力，不以模型回答逐字一致作断言，不进入默认离线 CI。

### 3.2 Agent、工具与 schema

- 事件顺序、单轮/多轮状态转换、工具结果与调用关联；工具失败、并发完成、重复响应、取消与完成竞争。
- schema 缺字段、类型错误、未知字段策略、深度和大小边界、Unicode、数字边界；不把 schema 验证错误混成网络错误。
- 工具超时、任务 panic/异常、channel 关闭及错误链传播；验证调用方可判断的错误、已有副作用和资源释放。仅在契约定义了隔离/捕获时要求捕获 panic，不制造“所有 panic 都可恢复”的承诺。
- 使用合成秘密标记注入配置、响应、工具错误和 URL；检查日志、错误展示、trace、快照、测试失败输出不泄露 Key/Authorization 等。夹具及原始结果不得含真实密钥。

### 3.3 存储与恢复

- 临时目录内验证真实追加、读取、重放、损坏定位；空文件、尾部半条记录、无效编码、未知版本、超限记录。
- 在追加前、中、确认后可控位置终止子进程，再重启读取；按设计声明的确认/持久化边界核验已确认数据、未确认数据和尾部修复策略，不能把 `flush`、进程崩溃与断电耐久性混为一谈。
- 短写、部分追加、磁盘满、权限拒绝、同步/rename 失败：通过窄 I/O 故障注入确定触发点，并在具备条件的隔离文件系统上补真实故障测试。不得填满宿主盘；无法运行真实磁盘满测试时标记限制。
- 两个真实写进程竞争、锁持有者崩溃、读写并发、取消写入；检查冲突处理、不丢失已确认记录、不交叉损坏。线程内 mutex 测试不能证明跨进程安全。
- 文件路径含空格、中文、组合字符；覆盖支持平台的路径、锁、rename、删除打开文件等实际语义。格式损坏不得静默删除完整历史。

### 3.4 子进程与终端

- 子进程大量同时写 stdout/stderr、无换行输出、非零退出、无法启动、超时、取消；不得因只读取一个管道而死锁。验证截断策略、输出上限与退出状态。
- 启动会再派生进程的受控 fixture，取消后检查进程树、管道、临时文件和句柄回收；明确 Unix 进程组与 Windows 实现边界，不把杀死直接子进程当作清理整棵树。
- 路径空格、参数引号、Unicode、无效字节的处理策略；分别验证直接进程启动和明确支持的 shell，不默认 shell 跨平台等价。
- 终端交互覆盖平台实际终端/PTY 或支持的 Windows 终端机制：宽字符、组合字符、emoji、缩放、粘贴、按键序列、Ctrl-C、异常退出后的终端状态恢复。终端快照可辅助，但不能替代真实输入/恢复验证。

所有异步/子进程测试都有总超时、独立资源目录和失败清理。超时表示失败，不能吞掉退出异常。同步点优先使用事件/屏障；避免以随意 sleep 掩盖竞争。

## 4. 风险驱动的增强验证

以下工具按风险选择，不要求每个模块全部使用；验收记录选择理由、工具链、支持平台、运行预算及未覆盖边界。

- proptest：适合分片无关性、编码往返、状态机合法转换等性质。生成有界输入，保存种子和缩减后的反例；往返测试不能代替独立的兼容性夹具。[官方介绍](https://proptest-rs.github.io/proptest/intro.html)
- cargo-fuzz：适合不可信字节、SSE/JSON、存储记录解析器。保存 corpus、崩溃输入和最小回归；固定时长/内存限制，先做有界运行。所选引擎、sanitizer、nightly 与目标平台的支持需核实，不假定三平台配置完全相同。[官方手册](https://rust-fuzz.github.io/book/cargo-fuzz.html)
- Miri：有自定义 unsafe、指针或别名风险时评估，用小型纯逻辑用例检查未定义行为；解释器支持有限，不能替代网络、FFI 或真实 OS 集成测试。记录未支持调用和跳过项，不把 Miri 通过写成安全证明。[官方说明](https://github.com/rust-lang/miri)
- Loom：有自定义共享状态/原子同步协议时建立小模型，使用其可观察的同步原语探索调度。状态空间、模型边界、探索上限必须记录；普通 Tokio 测试不会自动变成 Loom 检查，模型通过不代表所有生产交错已穷尽。[官方说明](https://github.com/tokio-rs/loom)

对普通安全代码和标准通道组合，清晰的集成/竞争测试可能已足够。新增工具应解决具体风险，不为检查表引入复杂基础设施。取消需要验证通知与等待任务结束两个环节，可参考 [Tokio shutdown 指南](https://tokio.rs/tokio/topics/shutdown)。

## 5. 差分测试与证据

为每个行为标识保存：参考文件/符号和固定提交、输入、预期事件/结果、Rust 入口、允许差异及原因。通过独立 checkout 或归档准备 TypeScript 基线，不切换或污染正在开发的工作树；准备构建依赖也须遵守仓库安全规则。

归一化仅处理双方认可的非语义差异，如时间戳、随机请求 ID 的具体值；保留 ID 之间的关联、顺序、错误类型、截断和副作用。不能排序本应有序的事件，也不能丢弃错误来使差分通过。

TypeScript 行为并非永远正确。发现基线缺陷时，保存最小反例，记录有意差异并评审；同时更新独立契约用例，不能悄悄修改对照版本。失败时保存双方原始脱敏输出与比较结果。

## 6. CI 门槛与真实平台验收

新的 Rust Agent workspace 建立后，将下列检查落实到相应 CI。现在的命令是未来执行范式，不表示这套新 workspace 或其 CI 已配置。先按设计生成实际 package/feature/OS 矩阵；默认功能、声明支持的最小功能和其他支持组合分别检查。不支持的组合明确注明，禁止机械使用 `--all-features`，尤其不能组合互斥后端。

默认功能组合的命令范式（在实际 workspace 根执行）：

```sh
cargo fmt --all -- --check
cargo check --workspace --all-targets --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo test --workspace --doc --locked
cargo build --workspace --release --locked
```

其他组合按实际契约使用 `-p <package>`、`--no-default-features` 和 `--features <supported-list>`，并对该组合执行相应 check、clippy、test、doc-test 和 build。二进制专用 package 无 doctest 时记录不适用。默认 `cargo test` 已包含常规文档测试；显式 `--doc` 作为可见门槛，避免改用 `--all-targets` 后遗漏。自定义 harness、ignored 测试和 feature-gated 测试须单独登记运行方式，默认命令通过不等于它们已执行。[Cargo test 文档](https://doc.rust-lang.org/cargo/commands/cargo-test.html)、[Clippy 用法](https://doc.rust-lang.org/clippy/usage.html)

- fmt、clippy 的警告及必选行为测试失败均阻止验收，不用全局 allow 或 ignored 隐藏回归。局部 lint 豁免须说明原因和范围。
- 对 Linux、macOS、Windows 的支持目标分别在真实对应 OS runner 上构建、运行测试和适用的进程/文件/终端用例，记录 OS 版本与架构。未覆盖的平台保留“待验证”；交叉编译成功只证明相应构建阶段，不能替代运行验收。
- 锁定并记录 Rust 工具链、Cargo.lock、Node/包管理器版本；声明 MSRV 时另跑适用的最低版本门槛。nightly 工具隔离为指定任务，不悄悄提高稳定构建要求。
- 测试不依赖开发者个人配置、真实 API Key 或公网模型；端口和临时目录隔离。重跑 flaky 测试不能掩盖首次失败，应记录原因、修复或评审阻塞。
- 文档变更只做适用的静态检查；不凭新增本规范声称执行过上面的命令。真正实施 CI 另属后续工作。

## 7. 每模块小规模 benchmark

### 7.1 对齐工作与环境

每模块至少有一个可复现的代表性对照场景，并覆盖适用的取消/失败/清理。纯类型和薄包装可引用所属模块场景，不制造无意义微基准。

Rust 使用 release 产物；TypeScript 使用固定基线实际生产运行方式。CLI 基线的 package bin 指向 `dist/bundle/cli.js`，库场景使用对应发布入口；具体构建、启动命令及产物摘要必须记录，不能默认以开发 loader 代表生产。Node 与 Bun 产物不能混用后统称 TypeScript 结果。双方在同机、同 OS、同资源限制运行相同输入、协议、校验、输出消费方式和并发量。

外部模型用本地 mock LLM 重放固定字节和事件节奏，隔离公网及模型服务延迟。至少区分无延迟吞吐场景和受控节奏的流/背压场景；服务端不能成为未说明的瓶颈。性能比较前先做结果一致性检查，不允许通过省略解析、校验、工具或落盘取得优势。

### 7.2 规模与测量

设计时填写具体输入字节数、事件数、工具次数、并发、运行次数、最大时长和磁盘预算。分两档：快速代表场景；有界的较大输入及边界场景（接近队列/输出上限、取消/错误/重试）。不默认开展大规模云压测。

- 冷启动：新进程从启动至就绪/首个可观察结果；将进程启动、首请求与完整短任务分别标注。新进程不等于冷文件缓存，未控制 OS 缓存时明确说明。
- 稳态：固定预热策略后测实际操作；双方都按预先约定预热，不能只给一方排除慢样本。构建耗时独立记录，不混入运行耗时。
- 记录 wall time、吞吐、适用的延迟分位数、CPU 时间/占用、RSS 与峰值、队列高水位、句柄/任务数。短任务和薄包装场景用于暴露启动、分配与调度成本。
- CPU 明确用户态/内核态、单进程/进程树和统计区间；子进程工具工作的成本不得隐去。mock 服务作为共同测量设施时单独统计其资源。
- RSS、峰值和采样间隔必须注明。进程树同时采样的 RSS 合计与各进程独立峰值相加不是同一个量；共享页面也可能重复计算。Windows 等平台的计数器须写准确名称与语义，无法直接对比时分开报告。
- V8 heap、Rust allocator 的分配计数和 OS RSS 不是同一指标。heap 小不等于 RSS 小；采样可能漏掉短峰值，工具缺失时写未测，不补估计值。
- 重复正常完成、取消、失败循环后采样稳态资源走势，记录已完成工作数、清理等待界限、缓存上限。区分有界缓存/分配器保留与随循环持续增长；不能仅用一次退出后由 OS 回收来证明无泄漏。

### 7.3 重复、噪声与判定

先用独立试跑估计耗时和波动，再冻结正式重复次数、预热、轮换执行顺序和判断规则；至少多个独立进程重复，不能单次取最好成绩。记录全部样本、失败次数、有效样本数、中心值和离散程度；样本足够时报告置信区间及方法。样本不足以支持 p99 或显著改善时直接说明，不给虚假精度。

正确性先过关，性能才有比较意义。预算由设计中的实际交互/资源需求决定；没有通用“Rust 必须快 X%”门槛，也不能把噪声范围内差别写成提升。CI 可先检查场景能运行、结果正确、硬资源上限及明显退化；共享 runner 上微小耗时差异由受控机器复核，不能盲目自动拒绝。

基准未达预算时先定位并修复；确有必要的权衡要记录原因、用户影响、证据、评审者和复查条件。不得降低正确性、秘密保护、持久化或取消基线来换取速度；未经评审的失败预算不能标成通过。

### 7.4 复现包

保留可执行 harness/脚本、完整命令、固定输入及摘要、双方提交与 lockfile/产物摘要、OS/架构/CPU/内存/运行限制、工具链和测量工具版本、feature/编译参数、时间、预热与重复策略、原始脱敏结果、统计方法及结论。说明测量工具的开销和缺失指标。模块验收链接到这份证据，不只放百分比截图。

结论只覆盖测过的场景和平台；未运行基准时写“未测”。文档、benchmark 框架、编译成功或预估数值都不能被称为性能验收完成。
