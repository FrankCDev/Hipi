# Rust 工程规范

## 适用范围与当前状态

本规范约束 Hipi 新建的 Rust 内核、模型适配层及其宿主集成。产品范围以 [VISION](../../VISION.md) 为准，仓库操作遵守根 [AGENTS](../../AGENTS.md)。这是实施和评审标准，不是已交付能力清单。

当前尚未建立 Hipi Rust 内核的 workspace 与对应验收流水线。仓库已有 `packages/env/daemon/Cargo.toml`，不能将它等同于新内核或其验收结果。本文的 Cargo 命令在新 workspace 建立后才适用；本次文档工作没有运行这些命令，也没有配置 CI。

“必须”是合入门槛；“优先”允许有依据的替代方案。例外应写明原因、影响、验证方式、负责人和重新评估条件，并在评审中明确接受。不能用例外静默改变 VISION 的产品边界。

所有 Rust 实现都以发挥 Rust 的语言特性和优势为优先：在保持范围内 PI 可观察能力与必要兼容的前提下，用所有权、强类型、enum、RAII 和明确的并发边界组织内部实现，不照搬 TypeScript 的类、对象层级或动态模式。语言特性服务于正确性、可维护性和实测表现；不为展示技巧引入复杂泛型、宏、生命周期或 unsafe，也不把全程零拷贝当作无条件目标。

## 1. 模块先设计，再实现

每个模块先提交 [模块设计](MODULE-DESIGN-TEMPLATE.md)，得到评审结论后开始实现。低风险模块通常一页即可；并发、持久化、协议解析、unsafe 等风险按需展开。设计至少说明契约、数据结构、所有权、状态转换、资源预算、复杂度及验收方法，不要求先写完整架构论文。

推进顺序为：参考行为 → 设计评审 → 最小完整实现 → 测试与小规模对照基准 → 定位并修正问题 → 记录验收。测试及 TypeScript 基准细则见 [TESTING](TESTING.md)。没有完成相应验收的模块不能被标记为后续模块的稳定依赖。

评审不是要求一次设计完美。测量或实现暴露问题时，先在所属模块做局部迭代；影响公共契约、依赖方向或预算时更新设计，并重新评审受影响部分。

## 2. 职责、依赖方向与 crate 边界

- 每个模块只有明确的一组职责，列出不负责的工作。解析协议、执行 Agent 状态机、管理终端交互不应混在同一层。
- 领域数据和状态转换不依赖 CLI、终端、全局配置、进程退出或具体厂商 SDK。宿主负责装配，模型适配器负责协议差异；内核通过必要的契约使用外部能力。记录实际依赖图，禁止循环依赖和向上依赖。
- 先使用 crate 内私有模块。仅当需要独立消费、清晰的依赖隔离、不同 feature/平台边界或独立维护时拆 crate；不要每个文件一个 crate，也不要为了目录对称拆空壳 crate。
- 内核作为库可嵌入：不隐式创建全局 runtime、不擅自安装信号处理、不调用 `process::exit`。运行时选择和宿主责任写入契约。
- trait、泛型和动态分发必须解决当前替换需求或测试边界。一个实现不自动需要 trait；确有宿主注入需求时也不以实现数量否定抽象。
- 新 workspace 统一 edition、最低支持 Rust 版本（MSRV）、依赖声明和 lint 策略；虚拟 workspace 显式选择与工具链匹配的 resolver。成员显式继承配置，不能只在根声明后假定已生效。workspace 管理方式参考 [Cargo 官方文档](https://doc.rust-lang.org/cargo/reference/workspaces.html)。

## 3. 公共契约、类型与所有权

- 默认私有，按需使用 `pub(crate)`，仅公开经过评审的 API。公开类型不要无意暴露内部容器、第三方客户端或运行时细节。
- 为易混用且具有不同规则的标识符、计量值和已验证配置使用 newtype；不要将所有字符串机械包装。构造时验证不变量，用 `TryFrom` 或返回 `Result` 的构造函数表达失败。
- 用 enum 表达互斥状态和事件，避免多个布尔值产生非法组合。状态转换写出前置条件、完成事件和重复调用行为。
- 优先借用只读数据、移动独占数据。`Clone`、`Arc` 和 `Mutex` 必须有用途，不能为逃避所有权设计把全对象放入 `Arc<Mutex<_>>`。共享不可变缓冲区可以用引用计数，但要计入存活时间和内存预算。
- 跨 `.await` 持有的数据、跨任务传输的数据以及可修改者必须明确。需要多线程调度的 future 满足 `Send`；若选择本地 `!Send` 执行，说明 runtime/线程限制。不要无条件给所有 trait 加 `Send + Sync + 'static`，也不要用 `unsafe impl Send/Sync` 修补不清楚的设计。
- API 写明事件顺序、单次还是多次完成、取消后能否继续使用、重入/并发调用支持、输入与输出上限。不要依赖调用者猜测流结束是否等于成功。
- rustdoc 必须覆盖公开 API 的用途、参数单位、不变量、错误、取消和资源语义；适用时写 `Errors`、`Panics`、`Safety` 及最小可运行示例。文档与类型一起评审，参考 [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/) 和其 [文档建议](https://rust-lang.github.io/api-guidelines/documentation.html)。

## 4. 错误、panic 与诊断

库的可判断错误使用结构化类型，例如区分无效配置、协议错误、超时、取消、资源上限和底层 I/O。调用者应通过 variant/字段处理，不能解析错误字符串。保留合理的 `source` 错误链，避免把整个响应正文或密钥嵌入错误。

CLI、任务入口等应用边界可添加操作上下文，或汇总为动态错误；不要因此抹掉内核中调用者需要判断的类别。重试依据错误类别、幂等性和总预算，设定次数/总时限与退避；取消、非法输入和不可重试错误不能无限重试。

来自用户、网络、文件或子进程的正常失败必须返回错误，不能用 `panic!`、`unwrap`、`expect` 处理。仅对可证明的内部不变量或测试断言使用 panic，并说明依据；公开 API 中可能 panic 的条件必须记入文档。不能通过全局捕获 panic 把程序缺陷伪装成正常结果。

## 5. 异步、背压与任务生命周期

例如，下游停止读取流后，上游仍持续接收数据：即使消息队列只有固定条数，单个消息无限增长仍会耗尽内存。必须同时约束消息数量、消息大小和在途总字节数，并说明超限时阻塞、拒绝、取消或按契约合并；不得静默丢失语义事件。

- 为队列、解析缓冲、工具参数、完整输出、缓存、任务数、打开文件和连接分别给出适用的预算、默认值来源、配置边界及超限行为。缓存需要容量和淘汰规则，TTL 不能代替容量限制。
- 并发许可应在启动任务或分配大资源前取得；把任务先全部 spawn 再等待 semaphore 仍可能无界积压。禁止无界 spawn、无界通道承接外部输入和无界 `collect`。
- 每个后台任务有所有者，负责观察成功、错误和 panic，传递取消并等待结束。采用 `JoinSet`、任务追踪器或等价机制，不把丢弃 `JoinHandle` 当作取消。
- 取消契约覆盖等待队列、等待许可、网络读取、工具执行和结果发送。评估 `select!` 分支被丢弃是否会丢失数据或半完成操作；超时返回不代表底层工作已停止。
- 关闭顺序写清：停止接收新工作 → 通知在途任务 → 在预算内排空或取消 → 等待任务 → 报告未完成工作。超时后是否 abort、终止子进程以及如何回收句柄必须有明确策略。取消与等待是两个步骤，参考 [Tokio shutdown](https://tokio.rs/tokio/topics/shutdown)。
- 不在异步调度线程执行长时间 CPU 工作或阻塞 I/O。使用有并发上限的隔离执行方式；已开始的 `spawn_blocking` 工作不能依靠 abort 强制停止，需要合作取消或可接受的结束上限。
- 默认不持锁跨 `.await`。确实需要异步锁覆盖 I/O 时，评审锁范围、锁顺序、等待上限和取消行为；“换成异步 Mutex”并不能自动排除死锁。短临界区可使用同步锁，并在 await 前结束词法作用域，参考 [Tokio shared state](https://tokio.rs/tokio/tutorial/shared-state)。
- 资源由 RAII 管理，但异步清理需要显式关闭与等待。`Drop` 只做可靠的同步兜底，不能假定进程异常结束仍会执行清理。

## 6. 数据结构与性能

设计写明实际操作：按 ID 查找、按顺序追加、删除、截断或广播，并据此选择容器。关键路径记录输入规模参数、时间复杂度、空间复杂度及分配来源；没有证据时选择简单实现。

流式文本或工具参数应增量组装和解析。禁止每个 delta 都复制并重新解析完整历史，导致累计平方级工作；如必须提供快照，说明按需生成/节流策略和测量结果。预分配要受可信上限约束，不能直接按外部声明长度分配。

每个模块在稳定依赖验收前进行适用的小规模 TypeScript 对照；纯类型和薄包装可由所属模块或真实消费路径覆盖。具体负载、统计和资源回收门槛见 [TESTING](TESTING.md)。发生退化先用 profiling 定位 CPU、分配、锁竞争或调度开销，再决定优化；不能只因 Rust 语言选择声称更快。

预算及性能门槛来自目标负载、基线和运行环境。设计记录目标、理由和测量办法，不全仓硬套任意延迟或内存数值；如果暂缺数据，明确标记待测，并在验收前补齐。

## 7. 文件、进程与跨平台行为

- 路径使用 `Path`/`PathBuf`，不假定 UTF-8、斜杠方向、大小写或 Unix 权限在各平台一致。处理符号链接、权限失败和并发访问；对不可信路径与进程参数明确允许范围。
- 先定义写入承诺：仅调用成功、读者不可见半文件，还是崩溃后可恢复。这些不是同一保证。
- 需要原子替换时，在同一文件系统创建临时文件，写入并检查错误后按平台支持方式替换，清理失败残留。不能用“先删除旧文件再重命名”冒充原子替换，也不能假定跨文件系统 rename 可用。参见 [`std::fs::rename`](https://doc.rust-lang.org/std/fs/fn.rename.html)。
- 需要耐久性时，明确用户态缓冲 flush、文件同步及目录元数据持久化的适用步骤和失败语义。`Drop` 不报告文件关闭错误；文件同步也不能替代所有平台的完整提交协议。按平台/文件系统验证承诺，参见 [`File::sync_all`](https://doc.rust-lang.org/std/fs/struct.File.html#method.sync_all)。
- 子进程必须有退出状态观察、输出容量限制、取消/超时及回收策略，明确是否终止进程树；Unix signal 与 Windows 进程管理分别验证。
- Linux、macOS、Windows 是真实运行验收目标。交叉编译只验证可编译，不能替代文件替换、进程取消或终端行为的本机测试。记录未覆盖项，不宣称三平台已通过。

## 8. 安全边界与 unsafe

模型认证仅支持 API Key；基础接入配置包括 Base URL、model ID 和必要的请求参数。厂商产品账号 Auth、OAuth、设备登录、订阅账号和账号令牌刷新不在范围内；Agent 内核及 AI 模块不得通过 Node.js 桥接复用 PI AI。独立 TypeScript 扩展宿主及 durable/chord 的实现映射仍按 VISION 单独评审。

API Key、Authorization header 及含密钥的 URL 不得进入普通日志、trace、错误显示、`Debug`、夹具或基准产物。请求/响应正文默认不记录；诊断使用脱敏字段和有界样本。可观测性指标标签不得放入密钥、完整提示词或无界请求 ID。协议解析要限制长度、嵌套深度及组装大小；不把外部内容当作可信配置或执行指令。

自有业务 crate 默认 `#![forbid(unsafe_code)]` 或等价 crate 级 lint。该规则不表示依赖、标准库或运行时没有 unsafe，也不替代依赖审查。

只有在安全 API 无法满足已证明需求时，才评审专用的小型底层封装例外；业务 crate 保持禁用。每处 unsafe 块说明 `SAFETY` 依据、别名/生命周期/线程不变量，每个公开 unsafe 接口写明调用者义务，由理解该不变量的评审者审查。适用时增加 Miri、边界/随机测试或 sanitizer 验证，并记录工具不支持的系统调用、FFI、平台等范围；工具通过不等于安全证明。不得为性能猜测提前引入 unsafe。

## 9. 工具链、依赖与供应链

- workspace 建立时选择并固定 `rust-toolchain.toml` 中的工具链版本，声明 `rust-version`/MSRV；不能把 edition 当作 MSRV。工具链升级单独审查，并在声明的最低版本验证受支持组合，参考 [Cargo rust-version](https://doc.rust-lang.org/cargo/reference/rust-version.html)。
- 提交 workspace 的 `Cargo.lock`，验证使用 `--locked`；版本声明、lockfile 和 feature 变化作为代码审查。直接依赖按仓库精确版本策略固定，成员共用 workspace 声明；不要将可变 git 分支作为可复现依赖。
- 只启用需要的 features，检查默认 features、传递依赖、重复版本、平台后端、native build 和构建脚本。按受支持组合验证；`--all-features` 仅适用于彼此兼容的 feature 集，不能替代 feature 矩阵。
- 引入依赖时记录用途、替代方案、许可证、维护与安全风险。更新时核对相关发行说明，避免只为消除错误而随意降级。
- 交付阶段保留依赖清单/SBOM、许可证与漏洞检查记录；工具选型和执行频率随发布流程落实，不为文档先搭重型系统。例外记录受影响范围、缓解措施和复查条件，不承诺扫描能证明无漏洞。
- 保留上游 MIT 许可证及版权归属。新增依赖的许可兼容性和随包声明纳入交付审查。

## 10. 工具门槛与完成定义

以下是 workspace 建立后的基础命令，在选定的 workspace 根运行。由实现阶段落实到脚本/CI；目前只是规范，不能据此声称检查通过。执行仍须遵守仓库及任务的命令授权要求。

```sh
cargo fmt --all -- --check
cargo check --workspace --all-targets --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo doc --workspace --no-deps --locked
```

- rustfmt 必须通过；Clippy 默认 lint 与项目选定 lint 的警告必须处理，不无差别启用全部 pedantic/nursery lint。局部允许项要附理由，不全局屏蔽。
- rustdoc 必须无警告，并对公开 API 启用 `missing_docs` 检查。CI 在进程环境设置 `RUSTDOCFLAGS=-Dwarnings` 后运行上面的 doc 命令；Windows 使用对应 shell 的环境设置方式。文档示例测试另按 TESTING 执行，`cargo doc` 不执行 doctest。
- 默认 features 通过后，还应验证承诺的无默认 feature/可选 feature/平台组合和 MSRV。命令及矩阵由实际 crate 名称和能力确定，不能用一个 workspace 命令代表所有组合。
- lint、构建成功不能替代测试和基准。完成前必须提供 TESTING 要求的契约测试、错误/取消/清理验证、适用对照基准和实际平台记录。
- 合入记录包含设计评审、受影响 API、运行命令及结果、基线提交、性能解释、已知限制；未运行、失败和通过分开列明。遗留风险有负责人及后续条件，不以“以后优化”跳过尚未解决的正确性或无界资源问题。
