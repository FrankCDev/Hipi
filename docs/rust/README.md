# Hipi Rust 规范索引

这些文档是后续实现和评审的执行标准，不是已有实现、自动守卫、CI 或性能验收的完成声明。

## 文档职责

- [项目愿景](../../VISION.md)：产品目标、同等能力、模型接入边界和冻结的 TS 参考提交。
- [AGENTS](../../AGENTS.md)：所有参与者必须先读的执行约束及详细规范入口。
- [工程规范](ENGINEERING.md)：模块、所有权、API、并发、错误、I/O、安全、依赖和工具链要求。
- [测试与基准](TESTING.md)：行为/差分/故障测试、公平 benchmark、可复现证据和平台验证。
- [资源安全](RESOURCE-SAFETY.md)：当前设备快照、重任务并发、资源阈值和缓存清理边界。
- [模块设计模板](MODULE-DESIGN-TEMPLATE.md)：实施前的问题、契约、预算、取舍及验证计划。
- [模块验收模板](MODULE-ACCEPTANCE-TEMPLATE.md)：实现后的证据、差异、风险和交付结论。

## 当前执行顺序

1. 先评估已有 Rust 成果，确认其对应的 PI/Durable 提交、能力、结构、测试和已知问题。
2. 对照目标能力建立差距清单，给出保留、局部重构或重写建议；没有证据时不预设从零开始。
3. 明确公开与私有资料边界。私有代码及其评估细节不会因可读取而自动获准公开发布。
4. 对确定要实施的模块完成设计和资源预算；评审高代价决定，必要时做有界技术实验。
5. 实现后执行正确性验证和适用的小规模 TS 对照，记录真实通过、失败及未执行范围。
6. 达到模块门槛后提交已授权的开发分支，并核实远端结果；阶段完成不等于完整产品发布。

已有实现与本仓库的 TS 参考版本不同，应先记录版本差异和可比范围，再决定是否调整基线；不能直接把不同版本的结果当成公平对照。

## 维护与交付纪律

- 一项规则只在负责它的文档详细定义，其他文档引用；变更时检查交叉引用和术语是否一致。
- 新依赖、许可、公开 API、持久化格式及平台承诺的变更须记录影响，不默默扩大兼容声明。
- 涉及持久化数据的升级先定义备份、版本识别、兼容范围与失败恢复；不可把旧数据能删除作为默认前提。
- 交付物须对应明确提交，附构建方式、版本/依赖信息、校验摘要、许可证、已知限制和已执行验证。
- 正式发布前另行落实安装、卸载、升级、数据恢复、原生平台运行及必要的供应链检查；当前没有发布批准。
- 日志和证据默认脱敏且有界。不得提交凭据、真实提示词或未经授权的私有资料。
- 例外记录理由、风险、批准者和复查条件；例外不能把未执行的工作变成通过，也不能擅自缩小产品目标。

当前不为了填满模板创建空 crate、占位实现或无意义测试。下一步决策以已有实现评估和实际设计证据为依据。
