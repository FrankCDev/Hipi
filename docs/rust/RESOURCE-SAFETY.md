# 开发环境资源安全与缓存清理

## 目的与适用范围

本规范用于避免 Rust 开发期间因并行编译、链接、测试或缓存增长耗尽环境资源。产品与工程要求仍以 [VISION](../../VISION.md)、[ENGINEERING](ENGINEERING.md) 和根 [AGENTS](../../AGENTS.md) 为准；资源不足时缩小单次执行范围或暂停，不降低功能与验收要求。

本文记录的是当前云端 Linux 开发环境，不是用户的 Mac。以下数据是一次快照，不是资源承诺；每次启动重任务前必须复测。本文没有实现资源守卫脚本、硬限制或 CI 自动保护，也没有进行安装、清理或测试。

## 2. 重任务启动与并发预算

重任务包括构建、链接、全量测试、基准和依赖安装。同一时刻只运行一个重任务；开始前检查本工作区已有任务，与其他执行者协调。不得为腾资源终止不属于本任务的进程。

每次启动前记录时间、工作区与输出目录、文件系统可用空间、`MemAvailable`、可读取的 cgroup 限额/当前用量，以及本任务预期的输出量和峰值内存。可使用 `df -B1 . /tmp`、`/proc/meminfo`、`nproc`，并按实际 cgroup 挂载和进程归属读取限制；读不到的字段标记“未知”，不能用主机总量填补。

- 初始编译并发使用 `CARGO_BUILD_JOBS=2`。链接或单个构建脚本仍可能占用大量内存，并发数不是内存上限。
- 测试线程另外限制为 `2`，例如适用默认 Rust 测试框架时使用 `-- --test-threads=2`。Cargo 的 jobs 只限制构建并发，不是测试线程上限；自定义测试框架、异步任务和子进程须分别限流。
- 基准单独运行，避免与构建、测试或安装重叠。先完成所需构建，再开始测量；保存本次环境、并发、原始结果和资源采样口径。
- 先执行范围明确的检查和小规模用例，再逐步扩大；全量执行仍须满足仓库规则与当次授权。
- 限制构建 profile、目标平台和 feature 组合数量，防止 debug/release、交叉目标和反复变更配置使产物倍增。必需的验收组合分批完成，不静默跳过。
- 同一兼容 workspace 优先共用其 `target`。不为节省空间建立复杂的跨不兼容工具链共享方案；记录自定义 `CARGO_TARGET_DIR`，避免误认其归属。
- 后续安装工具链时优先 minimal profile，按需增加 rustfmt、Clippy；先使用本机 target，其他 target 与工具链仅在确有任务需要时增加。本文不授权安装，也不代表已安装。

## 3. 保守初始阈值与停止条件

以下阈值是初始执行策略，不是实测峰值、性能验收标准或“不会宕机”的保证。`1 GiB = 1,073,741,824` 字节。

| 阶段 | 工作区/输出文件系统可用空间 | 系统 `MemAvailable` | 动作 |
| --- | --- | --- | --- |
| 启动重任务 | 至少 `8 GiB` | 至少 `3 GiB` | 两项均满足，且确认任务预算与实际配额适用后才启动 |
| 预警 | 低于 `6 GiB` | 或低于 `2 GiB` | 不追加工作，检查增长来源，准备取消或缩小任务 |
| 紧急停止 | 低于 `3 GiB` | 或低于 `1 GiB` | 取消本任务并等待其子进程退出，保留诊断后复测 |

如果发现实际容器限额更低，应以限额与当前用量重新制定预算，不能仅因主机 `MemAvailable` 达标而继续。大于这些余量的已知任务必须另行预算。配额未知时不能将上述启动条件视为充分保证；先采取更小规模执行并观察峰值。

执行者应在任务期间采样空间与内存，特别关注链接和大型输出阶段。采样守卫只能发现采样时的状态，不能阻止采样间隙的瞬时增长，也不能保证 OOM 不发生。自动守卫和 CI 尚未实现时，应明确记录人工检查、实际采样和未覆盖窗口，不声称自动保护已生效。

取消时只操作已确认属于本任务的进程及其子进程，先正常取消并等待；不得盲目按进程名杀掉所有 Cargo、Rust 或 Node 进程。若资源不足且无法安全恢复，应停工并说明缺口，不转移到 `/tmp` 无限继续。

## 4. 缓存清理顺序与授权边界

清理必须先确认“是什么、归谁、是否仍在使用、能否重建、是否获准删除”，不能看到大目录就删。

1. 盘点工作区及已知缓存目录的大小、文件系统和用途，区分源码、编译产物、依赖下载缓存、基准原始证据及未知内容；不跨无关目录盲目扫描或清理。
2. 列明候选目录的准确路径、归属、预计回收量和重建成本。确认没有活动构建、测试、基准或其他执行者在使用；先停止并等待本任务退出，其他任务协调处理。
3. 按当次明确授权清理范围确定、可重建的缓存，例如不再需要的旧 profile 或 target 产物。权限不清、路径共享、含未知内容或超出授权范围时先确认，不能推定整个 `target` 都可删。
4. 优先清理过期且重建成本低的产物。依赖下载缓存删除后可能需要重新联网、消耗时间并影响离线重建；不能作为默认第一步。不要盲目运行 `cargo clean`、全局递归删除或清空所有工具缓存。
5. 清理前后分别保存 `df` 结果，核对实际回收量；只凭删除命令成功不能声称空间已经释放。确认仍有足够余量后，才考虑一次有边界的重试。

以下内容不是普通缓存：源码、`.git`、lockfile、文档、测试、benchmark fixtures、基准原始结果和失败证据、用户文件、凭据。不得为了腾空间删除这些内容；永久数据删除始终另行确认。凭据不应进入清理报告或日志。

其他项目的删除授权不适用于本项目或新的缓存范围。本文不构成删除授权；范围明确的可重建缓存只能按当次授权处理。不得未经授权添加 swap、修改系统配置或更改资源限制。

## 5. 失败记录、复测与恢复

遇到磁盘不足、OOM、异常退出或取消，应保留脱敏的命令、时间、退出状态、已有错误日志、当时资源读数及产物路径。不要为了让重试看起来干净而删除唯一失败证据，也不要无限生成诊断文件。

先区分空间耗尽、内存不足、配额限制和普通编译错误，再决定是否清理或调整范围。恢复记录包含原因、授权的清理范围、清理前后可用空间、停止的自有任务及未完成验证。重新启动前再做完整预算检查；为重试预设次数和停止条件，资源未恢复或同一原因再次出现时停止并报告，不能无限重试。

后续环境或工作负载变化时更新实测记录与预算，保留日期和适用范围。只有实际检查、测试和基准结果能证明对应任务已完成；本文本身不证明实现通过验收或资源保护已经部署。
