# 首版验收清单

日期：2026-10-19。对应[首版范围](RELEASE-SCOPE.md)与[页面清单](SCREENS.md)。下列是待执行场景，当前全部 `not_run`；文档检查通过不能改变产品验收状态。

## 1. 如何记录结果

- 每个场景按实际平台、版本和 adapter 记录：`passed`（执行并满足断言）、`failed`（已执行且不满足）、`blocked`（有明确前置阻碍）、`not_run`（未执行）。不能以“待实现”算通过，也不能把单个平台的 passed 扩展到三平台。
- 记录源码提交/工作树差异、测试命令或人工步骤、OS/架构/硬件、依赖版本、语料与负载、实际观察、结果和证据的真实仓库路径或可访问链接。证据生成后才填写路径；不存在的测试、截图、日志文件不得写成已存在。
- P0：数据损坏、越权/秘密泄露、错误重做副作用、虚假成功等高风险，任何未解决失败均阻断发布。P1：核心闭环、恢复、跨平台、插件、可访问性与稳定性，首版范围内必须验收。P2：不影响操作的视觉细节，可记录责任人与修复计划后评审是否接受；不把核心主题/可读性缺陷降为 P2。
- 首版必需项的 failed / blocked / not_run 不能宣称已验收。例外要明确范围变更与用户影响，经评审决定；不能豁免未解除的数据和安全风险。

最小记录格式：`场景 ID / 平台与 adapter / 构建标识 / 步骤与输入 / 预期与实际 / 状态 / 证据路径 / 阻碍或缺陷`。一个场景含多个子步骤时逐项记录，未执行子步骤不可被整体 passed 掩盖。

## 3. 里程碑怎样使用清单

- 实施前先完成核心领域架构评审；明确会话/任务/执行与上游对象映射、状态持久化和生命周期。交互设计用 A01、A03–A06、A09–A11、A14–A16、A24–A25 检查可理解性。设计与原型评审单独记录，不能据此将本表产品验收设为 passed。
- 三个技术验证分别产出持久化恢复、双 adapter 契约、流式/编辑/预览的证据，关联适用场景；仅证明测过的边界，不自动通过整个场景。
- 纵向版本逐项补齐核心任务、文件、主题、国际化与插件证据；发布候选补齐完整支持矩阵及安全、恢复、安装更新与持续负载验证。
- 具体格式、OS 最低版本、语言、模型服务商与数值预算在[待决项](RELEASE-SCOPE.md)中评审。明确范围后为矩阵逐格建记录；未定预算只能报告测量结果，不能声称性能达标。
- 所有命令遵守[仓库规则](../../AGENTS.md)与[开发规范](DEVELOPMENT-STANDARDS.md)。本清单不授权安装依赖、生产构建、调用付费服务或运行禁止的测试。
