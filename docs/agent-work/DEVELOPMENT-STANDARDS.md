# 开发规范与评审标准

日期：2026-10-19。适用范围：Hipi Work 客户端及其接入代码。本文将[工程原则](ENGINEERING-PRINCIPLES.md)转成可执行的开发与评审要求，参考专业团队的公开实践，并按本产品风险裁剪；不是照搬大型组织流程。

**必须 / 不得**是约束；**应**是默认做法，偏离时在变更说明中解释理由与替代验证；**候选 / 待实施**不是已经启用的工具或门禁。根目录 [AGENTS.md](../../AGENTS.md)的命令、依赖、导入与 Git 规则继续有效；冲突时先澄清，不能以本文为由绕过它们。本文新增客户端规范，不证明现有代码全部符合，也不证明 CI 已自动检查这些要求。

阶段划分可以缩小功能范围，但不得降低正式代码的封装、类型、持久化、错误处理、资源生命周期与测试标准。封装应体现职责、所有权和不变量，不以包装层或接口数量衡量。交互原型、确定性测试模型和兼容性实验必须明确标识并与正式组装隔离，不能用模拟结果代替真实核心链路，也不能把实验通过宣称为生产客户端完成。

## 1. 模块、目录与公开接口

- 必须遵循[架构边界](ARCHITECTURE.md)：UI → AppClient / 应用契约；传输 adapter → 应用核心入口；应用核心 → 自己定义的端口；平台、存储和 Durable adapter 实现端口。组装入口连接实现，核心不得反向依赖 adapter。
- UI、应用契约和 AppClient 不得导入 Electron、Node 内置模块、preload 或宿主实现；应用核心不得依赖 Electron 或 HTTP 框架。不得靠类型断言或转导出来掩盖越界依赖。
- 模块必须明确公开 exports；跨模块只能使用公开接口，不深层导入私有文件，不形成循环依赖。公开契约只暴露必要数据和行为，不导出数据库、进程或运行时内部对象。
- 应按功能组织 UI 与对应测试，再在功能内部按需要分组件、状态和适配；真正共享的契约与基础组件单独放置。不提前为每个目录建包，也不把业务逻辑堆进全局 `utils`、`common` 或巨型 service。
- 只有出现可说明的共同职责或变化点时才抽象。新增抽象应能用具体调用例子解释收益；不为假想插件、微服务或未来多租户增加当前无用层级。
- 依赖方向自动检查尚待实施；此前必须人工检查变更中的 imports / exports。受控浏览器构建验证应在获准实施后加入门禁，不能仅靠 TypeScript 编译认定无 Node 依赖。

## 2. TypeScript、数据与代码可读性

- 客户端新代码必须采用 TypeScript 严格检查；实施时审查有效 `tsconfig`，不得为消除报错关闭严格性。`strict` 的作用与升级注意事项参考 [TypeScript 官方文档](https://www.typescriptlang.org/tsconfig/strict.html)。新增配置仍需单独验证，本文未修改配置。
- 不可信输入先按 `unknown` 处理，经共享 schema 运行时校验后进入用例；类型断言不是校验。IPC / HTTP 使用同一公共契约，TypeBox 为推荐 schema 基础，具体校验链路仍待验证。
- 不得使用 `any`、非空断言或连续强制转换掩盖未建模状态；确实无法避免的边界例外应局部封装，注明原因并提供测试，不能扩散到业务层。
- 使用可区分联合表达互斥状态；区分缺失、空值、未加载、失败与结果未知。ID、时间、单位和版本字段语义必须明确，不凭字符串格式猜测来源。
- 命名描述业务意图；注释解释原因、约束或不可直观发现的行为，避免复述代码。函数与组件保持可理解的职责，不设机械行数或文件数量目标。
- 根规则要求顶层 imports，禁止 inline / dynamic imports；延迟加载需求必须先提出兼容方案或获得规则变更确认，不能因为候选库示例使用动态导入就直接照搬。根配置覆盖的代码继续只用可擦除 TypeScript 语法。

## 3. 异步、错误与资源生命周期

- 每项异步操作必须说明由谁拥有、何时结束、如何取消和清理；Promise 必须被等待或由明确的后台监管者捕获失败，不允许未处理 rejection。
- I/O 应设置有依据的超时；区分客户端停止等待与执行取消。超时不能直接标记外部操作未发生。重试必须有上限、退避和适用的幂等或结果核对依据。
- 并发、队列、订阅、缓存与流式缓冲必须有边界；任务取消、页面卸载、连接切换和进程退出时释放监听器、计时器、worker、文件句柄及对象 URL。测试慢消费者和取消竞争条件。
- 错误必须提供稳定 code、关联 requestId / taskId、可安全展示的说明与必要的恢复动作；内部 cause 保留在受控诊断中。不得将完整异常、凭据、私有文件内容或敏感路径直接回传 UI 或日志。
- 日志应结构化并标明事件、阶段与结果；默认脱敏，不用自由文本拼接秘密。对于“结果未知”，必须保留核对入口，不能简单吞掉错误或自动重做副作用。

## 4. 契约、持久化与安全

- 变更 schema 必须检查 IPC / HTTP 两个 adapter、持久记录与订阅消费者。明确当前支持的协议版本及不兼容时的拒绝或升级行为；不因此默认维护用户未要求的旧版兼容层。
- Durable 是持久执行事实的单一权威；UI 缓存只能重建投影。新增元数据必须明确所有者、事务边界与单写入策略，不复制第二套任务生命周期。
- 存储变更必须有版本、迁移前置检查、备份 / 恢复方案及失败测试。不可逆迁移必须显式说明，旧应用能启动不等于能安全读取新数据。
- Electron renderer 必须关闭 Node 集成、启用上下文隔离和适用沙箱，使用限制性 CSP；验证 IPC sender、参数、授权与导航 / 新窗口目标。preload 仅暴露最小逐项能力，不暴露原始 IPC 或任意文件访问。具体实施依据 [Electron 安全清单](https://www.electronjs.org/docs/latest/tutorial/security)，仍需产品威胁模型和测试。
- 不可信 Markdown、文档、图片与插件资源遵循[工作台安全要求](WORKBENCH.md)，不能靠进程隔离替代权限校验。凭据不进入源码、普通配置、日志或诊断导出。

## 5. 组件、主题与国际化

- 组件 props 必须有明确类型与职责；避免大量布尔开关组合出非法状态。受控输入与本地草稿的所有权明确，不复制可推导数据。
- 使用 React 时必须遵守组件 / Hook 纯度、不可变 props / state 和 Hooks 调用规则；副作用不发生在 render，effect 的订阅必须清理。专项 lint 与 Strict Mode 的接入需另行验证。[React 官方规则](https://react.dev/reference/rules)
- 必须使用语义主题变量，支持全局及约定区域的字体、配色、背景覆盖与回退；不在功能代码散落固定颜色或字号。组件须覆盖加载、空、错误、禁用、焦点与长内容。
- 用户文案使用稳定英文层级 key，不把展示文案作为 key，不拼接句子；日期、时区、数字与复数使用语言环境格式化。必须验证中文输入法、长译文、缩放及字体回退。
- 必须使用恰当语义、可访问名称、键盘操作和可见焦点；对话框与文件工作台应验证焦点进入、退出与恢复。不以鼠标可点击或截图好看来代替无障碍验证。

## 6. 测试与质量门禁

测试以用户行为和风险为目标，不追求测试数量或单一覆盖率数字。纯规则用单元测试；IPC / HTTP 共用契约用一致性测试；真实用例用集成测试；关键工作闭环用端到端测试。确定性假模型优先，真实服务与付费测试必须隔离并获授权。

必须按变更影响验证：授权拒绝、重复请求、回包丢失、存储失败、runtime 崩溃、重启恢复、断线与重连、取消、事件缺口、文件版本冲突及副作用结果未知。修复缺陷应加入可复现的回归测试；测试应验证结果而非过度绑定内部调用顺序。

**待实施的客户端 CI 门禁目标**：

- 普通代码变更：格式 / lint、严格类型、模块依赖边界、相关单元及契约测试；有跨模块影响时增加集成测试。
- UI 变更：关键交互与可访问性检查；布局、主题、字体或国际化变更增加视觉回归，截图不能替代行为断言。
- 安全、迁移、执行恢复或打包变更：对应故障测试、关键端到端路径及相关平台打包验证。
- 发布候选：获准的生产构建、三平台安装 / 启动 / 更新与关键工作流验证。Windows、macOS、Linux 须有真实目标系统运行证据；涉及原生窗口、输入法、权限、通知、签名或硬件行为时做对应真机检查，不能仅以 mock 或单平台结果替代。

上述是门禁设计，尚未配置或确认运行；实施时列明实际 job、命令、平台矩阵和阻断条件。失败不得通过删除断言、跳过测试或降级依赖来伪装通过。临时例外应说明风险、替代验证与修复责任，安全或数据损坏风险未解除不得发布。

本地执行始终遵守根 AGENTS.md：代码改动后运行其规定的 `npm run check`；没有用户要求不得运行 `npm run build`、`npm test` 或完整 vitest。新增 / 修改测试按根规则运行具体文件。本文不是提前授权执行这些命令。纯文档只检查内容、链接与 `git diff --check`，不宣称功能测试通过。

## 7. 变更与代码评审

应保持变更小而完整：一个可解释目标，避免混入无关重构、批量格式化或依赖升级。评审关注设计、正确性、复杂度、测试、命名与文档；不把个人风格偏好当成阻断理由。参考 [Google 评审要点](https://google.github.io/eng-practices/review/reviewer/looking-for.html)与[小变更实践](https://google.github.io/eng-practices/review/developer/small-cls.html)。

每次变更说明应简短回答：

1. 解决什么问题，用户可观察到什么变化？
2. 改到哪些边界，有没有权限、数据、契约或兼容风险？
3. 运行了什么验证，结果如何；什么未运行及原因？
4. 需要时如何恢复，哪些限制或后续工作仍未解决？

小型文档或样式修正可用几行说明；权限、外部副作用、迁移、插件加载和发布更新属于高风险，应补充失败场景与恢复证据，并获得相关责任人的重点评审。不要求每个 PR 填巨大表格，不为低风险改动创建形式化设计文档。

提交、分支和协作继续遵守根规则：仅在用户要求时 commit；只暂存自己修改的明确路径；提交消息使用现有 `{feat,fix,docs}[(ai,tui,agent,coding-agent)]` 约定，新客户端 scope 另行确认。不得强推、跳过检查、清理或覆盖其他会话工作；未获明确要求不切换工作树去检出 PR。本文未新增分支保护配置，也不改变发布权限。

## 8. 依赖、工具与供应链

- 新依赖必须说明用途、替代方案、维护状态、官方来源、许可证、体积和安全影响；审查新增传递依赖与 lockfile，不能只看顶层包名。依赖漏洞需评估可达性与影响，并给出修复或缓解方案。
- 直接 registry 依赖及内部 workspace 依赖按根规则固定确切版本，lockfile 必须可审查；不引入第二套包管理器，不用浮动范围掩盖兼容问题。升级需核对官方变更说明并运行受影响验证。
- 安装使用根规则规定的 `--ignore-scripts`；生命周期脚本不能自动执行，需要单独审查和用户允许。更新 lockfile 与安装锁文件时遵守现有脚本及 allowlist 流程。
- Biome 负责唯一格式化与基础 lint 是当前推荐；ESLint 只补充无法覆盖的 React Hooks / TanStack 等专项规则，明确范围并关闭重复规则。不与 Prettier 对同一文件重复格式化。具体配置仍待实施，不得声称已有自动保障。
- 发布依赖清单、来源及构建元数据应可追溯；供应链风险评估参考 [OWASP 软件供应链安全指南](https://cheatsheetseries.owasp.org/cheatsheets/Software_Supply_Chain_Security_Cheat_Sheet.html)。固定版本与自动扫描不能替代依赖审查，也不自动证明安全。

## 9. 发布与交付证据

- 发布必须能关联源码提交、依赖锁、工具链和构建产物；验证适用的平台签名、公证与产物完整性。签名凭据由受控环境管理，不放入仓库或普通日志。
- 更新必须验证来源与完整性，并覆盖下载中断、安装失败、版本不兼容及启动失败。数据迁移先明确备份和恢复边界；应用回退与数据恢复分别验证，不能声称任意降级都安全。
- 发布记录必须列出支持的平台、已知限制、验证证据和恢复方式；不能凭一次启动、演示或文档声明生产就绪。发布脚本、自动更新和门禁的真实完成状态另行记录。
- 完成报告必须区分已实现、已验证、候选、未验证与已知风险。规范会随实际证据修订，但不得为赶进度悄悄降低数据、安全与恢复标准。
