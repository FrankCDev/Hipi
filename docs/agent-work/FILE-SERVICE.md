# Local file service boundary

The first file slice is implemented in `packages/work-runtime/src/files/`: browser-safe DTOs and a pure Node authority. Its separate FileClient is wired through the authenticated loopback HTTP endpoint and shares strict request/response validation with desktop integration. File access is not part of the general AppClient method surface. Tests use temporary fixtures only.

## Authority and identity

The trusted host constructs one `createFileAuthority` per application runtime and binds `forPrincipal` to the authenticated connection identity. `assertWorkspaceAccess` is checked for every request and again before publishing a read or committing a write. The host must reject access after workspace/session revocation.

Only a trusted native folder picker, verified host-owned project binding, or explicit server-side host configuration calls `grantRoot`. Public IPC/HTTP must never accept an absolute root path or caller-supplied principal. A grant returns only `workspaceId`, opaque `rootId`, and `writable`. The canonical filesystem root is private and is separate from workspace/storage identity. Grants are in-memory and expire on restart; they are never reconstructed from renderer preferences. A persistent project binding can issue a fresh read-only grant after the trusted host validates its saved canonical directory identity. `revokeRoot` prevents new calls and pending commits after the last grant check; it does not undo completed I/O.

The public port is `listRoots(workspaceId)`, `list(target, cursor?)`, `readText(target)`, `saveText(target, text, ifMatch)`, and `preview(target)`, where target contains `workspaceId`, `rootId`, and a slash-separated relative `path`. Root discovery returns only grants for the authenticated principal and authorized workspace. Authority `close()` revokes grants, rejects new work and waits for admitted operations to settle. The empty path is accepted only for listing the root. No URL decoding or path normalization occurs. Traversal, absolute/drive/UNC paths, percent encodings, NUL/control characters, lone surrogates, Windows device names, alternate data streams and ambiguous trailing dots/spaces are rejected. Symlinks below the authorized canonical root, nonregular files and multiply-linked files are blocked. A trusted picker may select a root through an OS alias; its canonical directory becomes the grant, and its identity is checked thereafter.

## Public transport and explicit host configuration

`/files` accepts POST JSON only after the existing exact Host, Origin and bearer-capability checks. The file protocol is version 1, separate from the application protocol. Every request includes `expectedStoreId`; every response binds the store, method and exact workspace/root/relative-path target. Unknown fields and error codes are rejected. Neither a principal nor an absolute filesystem path is accepted in public requests. Responses are bounded to one MiB and use `Cache-Control: no-store`.

`createRuntimeFileHost` creates one authority per runtime generation and binds a trusted host principal. Its authorization check reads the current workspace catalog without opening a workspace or resuming execution. A missing workspace is denied. Root IDs cannot be reused across authorities, generations or stores. Shutdown first stops incoming requests, then revokes and drains the file authority before closing the runtime.

The loopback acceptance CLI defaults to no granted roots. To grant access, first create a workspace through the application and record its workspace ID, then restart the host with an explicit mapping. For a POSIX shell, append this argument to the existing provider/origin/data invocation:

```sh
--file-root '{"workspaceId":"existing-workspace-id","absolutePath":"/absolute/project-folder","writable":false}'
```

Use `writable:true` only when explicitly authorizing replacement of existing text files. Repeat `--file-root` for additional mappings. JSON must remain one shell argument; other shells may require different quoting. The workspace must already exist in that runtime's catalog. Invalid mappings fail closed with stable codes without echoing filesystem paths. There is no home-directory fallback or implicit root for an unbound project. Native desktop folder selection is a separate trusted grant path, not a public absolute-path parameter.

## Persistent desktop projects

New project optionally selects a local folder before Create. Cancelling the picker preserves the draft without creating a project; an intentionally folderless project remains a conversation group. The existing project menu's Project folder action binds, changes or disconnects a folder. Only the native picker supplies its path to the trusted host. Before creation, the renderer receives a short-lived opaque selection token, not a filesystem path. A confirmed project creation followed by an uncertain binding reply keeps the same project and offers a read-only check instead of creating again.

The catalog stores the private canonical directory identity separately from live roots. Reopening validates that identity and creates a new read-only root scoped to the selected project; moved, replaced, unavailable or revoked folders require explicit recovery rather than silently falling back to another root. Disconnecting a folder preserves conversations and requires review of unsaved editor buffers. It does not delete files. Backup restoration produces a non-executing archive and does not restore folder access.

Binding lets the user browse locally. New conversations created inside that project receive default read access as a private creation policy, not a renderer-created grant or a separate consent RPC. The trusted host resolves the current verified project binding and supplies only bounded root metadata and relative paths to the model, never its absolute path. This default is read-only, does not cover external roots, and does not appear as a fabricated entry in explicit context-grant history. Disconnected, revoked, moved or unavailable bindings remain inaccessible. A known explicit revocation for that conversation and binding is not silently undone.

The new-chat composer has no project authorization control, dialog or staged consent. Ordinary Send passes the text and selected model into the existing first-send owner; conversation creation owns the project default. Opening the composer, choosing a model, cancelling or reloading does not send, create a conversation or authorize access. Existing conversations with ambiguous project-file history are not retroactively authorized; the explicit and retained-context safeguards still apply. Writable local roots remain available through the file panel's explicit Folder access picker; Agent writes additionally require explicit context and the existing per-call approval flow.

Previously saved initial-consent journals remain recoverable. Their original scope, model, paths, expiry and request identities are preserved for exact outcome checks and explicit recovery, never automatic resends. Proven pre-submit recovery can keep a draft; if a newer draft conflicts, an explicit combine action preserves the newer text first and appends the original unsent text without sending either. Removing the new composer's consent flow does not discard these journals or weaken their prerequisite checks.

The browser-safe `createHttpFileClient` requires the same handshake `storeId` as the application connection. `createFileClient` provides the same validation and bounded waiting for a desktop bridge. Optional AbortSignal and the ten-second client deadline stop waiting, not admitted filesystem I/O. Save cancellation, transport loss or an invalid response after dispatch returns `WRITE_OUTCOME_UNKNOWN`; there is no automatic retry. A pre-aborted signal admits no request. Confirmed service errors such as `VERSION_CONFLICT` remain distinct.

## Reads, saves and resource bounds

Reads accept strict UTF-8 text only, preserve BOM and line endings, and reject binary control bytes and malformed encoding. SHA-256 of the exact bytes is the revision. Reads use a bounded buffer and check file identity and timestamps before/after reading. Errors contain stable codes, never raw OS exceptions or absolute paths.

Limits are currently conservative engineering guards, not measured performance promises: 128 KiB per text file, 50 entries per page, 4,096 scanned directory entries, 32 root grants and 8 concurrent operations. Excess concurrent work is rejected with `BUSY`, without an unbounded queue. Larger directories are explicitly rejected rather than silently truncated. Directory cursors bind the root, relative directory and ordered entry metadata; changed membership invalidates the cursor. They are not durable filesystem snapshots. UTF-8 and path bounds keep individual result frames below the existing one-MiB transport budget, including JSON escaping.

Saving supports existing text files only. It requires a writable grant and exact `ifMatch`; concurrent service writes to the same inode are mutually excluded, including overlapping grants. The service checks the old revision, writes an exclusive same-directory temporary file, preserves ordinary permission mode bits, syncs and closes it, rechecks authority and the current disk revision, then renames it over the target. A stale revision returns `VERSION_CONFLICT` without overwriting the disk file; the caller must retain its dirty buffer. There is no force-write, creation, delete or revert API. Temporary cleanup is best-effort; crash leftovers are not automatically removed from user folders.

Rename errors return `WRITE_OUTCOME_UNKNOWN`, not a claim that no write occurred. The editor must retain its buffer and reread before deciding what happened; it must not blindly retry. A successful return confirms the rename call completed, not survival of power loss, replication or a subsequent external writer. No directory fsync, ACL/xattr/owner preservation, network-filesystem guarantees or cross-process transaction is claimed. These need platform-specific review before broader deployment.

## Trusted Agent commit boundary

`forAgent(principalId)` is a Node-only port for the trusted authorization broker. Its list/read methods share the manual service; its save requires a `FileCommitPermit` callback. This capability is not exported through the browser file contracts or public file transport. Neither renderer nor model arguments may supply a callback, approval identity, principal or absolute path.

Its synchronous `assertRoot(workspaceId, rootId)` checks current in-memory grant liveness, principal/workspace binding and authority closure. The broker uses it after asynchronous authorization checks and immediately before synchronous model dispatch, with no intervening await, so a stale `listRoots` result cannot authorize dispatch after root revocation. It performs no filesystem I/O and does not replace workspace, context, task or physical root identity validation. Regranting the same directory produces a new root ID and never revives the old one.

The service prepares its same-directory temporary file using the existing bounds, encoding checks and inode write exclusion. It then invokes the broker's permit with a single-use commit closure. The broker must check the exact task/call/arguments, current task cancellation, consumed approval and context version under the same mutex used by context revocation and cancellation, and retain that mutex while invoking and awaiting the closure. The closure repeats file authorization and `ifMatch`, checks that the original root grant still exists, and starts rename without yielding after that last root check. Checking permission before calling save, or releasing the mutex before awaiting the closure, is insufficient.

Cancellation/revocation that wins this gate prevents replacement and cleans the temporary file on normal unwinding. Once the guarded commit wins the mutex, later cancellation must wait and cannot promise rollback. Root revocation independently blocks commits up to the last root check. Any failure after rename starts, including a permit that loses its acknowledgement after a successful rename, returns `WRITE_OUTCOME_UNKNOWN`. The broker owns durable operation evidence and confirmation; this service does not create another operation store or retry saves. Authorized reads return the exact current hash for later reconciliation; a matching hash is an observation, not proof of which writer produced it. In-process cleanup is best-effort and does not cover process crashes.

## Security and race limits

The supported mode is explicitly `cooperative-local-files`: a trusted local user's editor and authorized tools. Pure cross-platform Node path checks plus rename cannot eliminate symlink/parent-directory races with a hostile local process, nor can a content recheck make rename an atomic compare-and-swap against external writers. A noncooperating writer can modify the file in the final check-to-rename window. The service does not provide an OS sandbox. Multiple authority instances must not be assembled against the same resources as if they shared the in-process write guard.

Hostile same-user process protection requires a separate native handle-relative broker and OS isolation with platform-specific evidence. This module must not be exposed as that protection. Regular local filesystem I/O is bounded by bytes and concurrency but cannot be force-cancelled safely through this API; stuck mounts require host supervision. Windows/macOS filesystem and permission behavior remain unverified by the Linux fixture tests.

## Diff and previews

Trusted Node preview consumers obtain `forPrincipalSnapshot(principalId)` from the same authority. Its `read(target, maxBytes)` shares the existing grant, principal/workspace, relative-path, root identity, symlink/hardlink, bounded concurrency and before/after file checks. It returns independently owned binary bytes and their exact SHA-256 revision, without exposing a filesystem path or decoding the content. The caller must supply a trusted internal integer budget between one byte and 20 MiB; runtime validation rejects invalid or larger budgets. This port is not exposed through the public text contracts or transport, whose 128 KiB text limit is unchanged.

Snapshots are read results, not continuing authorization. A preview service retaining bytes must bind them to the exact target and revision and call `assertAuthorized(target)` before publishing each later resource or chunk. This checks current workspace access and root grants, and detects authority closure; a TTL alone cannot authorize cached reads. Revocation blocks pending reads at their publication check and later accesses, but cannot retract bytes already delivered. The preview service owns immutability, cache quotas, disposal and parser cancellation. File snapshot bounds do not establish parser resource limits or OS sandboxing; the cooperative-local race limitations above still apply.

`EditorDiffBaseline` is explicitly `editor-read`: the exact target, revision and text originally read. Comparing it with a dirty editor buffer is not a task-before/after diff and is not Git HEAD. Task and Git baselines require separate evidence and are not implemented by this module. A conflict does not replace this baseline or the user's buffer automatically.

The initial file `preview` method still yields strict text with `rendering: plain-text-only`, or an unsupported binary/encoding result. Even HTML/SVG is inert text, never an HTML document or file URL. Consumers must render escaped text with no external requests and no execution.

A separate bounded preview service in `packages/work-runtime/src/previews/` now uses authorized immutable snapshots and exposes dedicated HTTP/desktop contracts. DOCX projects plain text; XLSX projects bounded cells and cached formula values without recalculation; CSV projects strings. The UI connects these projections plus PDF/image preview paths through `DocumentPreviewPane`. See [parser formats and limits](../../packages/work-runtime/src/previews/README.md) and [dependency review](DEPENDENCY-REVIEW.md). This is restricted read-only preview, not full Office fidelity, macro execution or editing. Worker threads are not an OS sandbox. Resource identity, authorization rechecks, disposal and cancellation remain required; targeted parser/service/transport tests do not prove actual browser rendering, malicious-input completeness or cross-platform release readiness.

The UI file workbench connects authorized roots, CodeMirror editing, dirty-buffer protection and version-conflict handling. Existing text-file replacement and the `editor-read` Diff baseline retain the limitations above. No Agent file tools or plugin lifecycle are implied by the manual editor integration.

## Evidence

Run the targeted fixture suite with `node --conditions=source --test packages/work-runtime/test/files.test.ts`. It exercises authorization, path ambiguity, symlink/hardlink/root replacement rejection, UTF-8/BOM handling, limits, pagination, stale versions, concurrent saves and inert text previews. These checks do not prove hostile-process race resistance or three-platform release readiness. Run `node --conditions=source --test packages/work-runtime/test/files-transport.test.ts` for strict schema and response identity, cancellation/unknown save, explicit CLI mapping, JSON frame bounds, and real temporary-file HTTP list/read/save/conflict/authentication/generation checks. Desktop picker and editor state have their own integration evidence; the repository-wide check remains a separate gate.

Run `node --conditions=source --test packages/work-runtime/test/files-snapshot.test.ts` for binary fidelity and independent ownership, exact revisions, trusted byte budgets including the 20 MiB ceiling, unchanged text limits, authorization/revocation, close draining, unsafe resource rejection and a deterministic mutation of a real temporary file during reading. The latter coordinates mutation through a test-only file-handle method mock; it is regression evidence for the checks, not a claim of hostile-process race immunity.

Run `node --conditions=source --test packages/work-runtime/test/files-agent.test.ts` for missing/denied final permits, deterministic cancellation and revocation ordering through a fixture mutex, inode exclusion against manual saves, external edits while waiting, root revocation, lost post-rename acknowledgement and temporary-file cleanup. The fixture proves the file-side callback boundary; the production broker must additionally verify its persisted authorization facts and serialize its real cancellation/revocation commands.
