# 工程原则

本文定义 Hipi Work 客户端的工程质量约束，配合[产品原则](PRODUCT-PRINCIPLES.md)与根目录 [AGENTS.md](../../AGENTS.md)执行。目标是可维护、可验证的生产级产品；本文不证明当前实现已达到这些标准。

具体代码、组件、测试、评审、依赖与发布要求见[开发规范](DEVELOPMENT-STANDARDS.md)；规范目标与已经落地的自动检查必须分开报告。

## 1. 先明确边界，再选择技术

- Electron 桌面、TypeScript 主进程及 shadcn/ui、Tailwind CSS、TanStack 家族方向已明确；具体边界与推荐方案见[架构决策](ARCHITECTURE.md)。UI 与核心不依赖 Electron，IPC/HTTP 通过应用契约适配。具体版本与工具仍须验证跨平台体验、运行时兼容、安全边界、可测试性、维护成本和性能，并记录证据与取舍。
- 按职责划分界面、应用用例、领域状态、运行时适配、持久化和平台能力。模块边界服务真实变化，不为假设需求提前堆叠框架或抽象。
- 业务规则与权限判断不得散落在 UI 组件中；UI 临时状态与持久执行状态分离，界面重载不能改变执行事实。
- 采用清晰命名、明确类型、统一格式与错误处理、可审查的小变更。遵守仓库现有代码规范，避免不必要的隐式行为与重复状态源。
- 样式同样需要封装：先查现有主题配置与设计变量，再通过基础值、语义和组件 token（具名设计变量）集中表达视觉决策。参考界面的测量值用于校准 token，不在各处写死后反复批量调整；内部 token 不等于用户可配置项。具体分层、例外与验证要求见[开发规范第 5 节](DEVELOPMENT-STANDARDS.md#5-组件主题与国际化)。

## 2. PI Durable 通过薄适配层接入

- 当前文档基线为 `1402973a9dbe8c627341e04c9744c54953e285ca`，不是对未来上游状态的描述。
- [PI Durable README](../../packages/durable/README.md)在该基线标注 Experimental。必须固定上游 SHA 或经验证的确切版本，明确 API 风险。
- 产品通过薄适配层调用运行时，集中处理类型、状态映射、错误与生命周期，避免把上游内部细节扩散到 UI。
- 升级需审查变更，并运行契约、持久化、恢复及平台回归；不能仅靠类型检查通过认定兼容。
- 不因接入 Durable 就承诺端到端 exactly-once。运行时恢复、请求去重和外部系统副作用是不同问题，必须分别验证。

## 3. 协议与执行状态明确

- 进程间通信（IPC）使用类型化契约、运行时 schema 校验与协议版本；校验来自 UI、插件与其他进程的边界输入。
- 设计稳定标识、请求关联、事件序号、幂等规则与错误结构，处理重复、乱序、缺失、重连和背压。
- 以持久事实恢复视图；定义快照与增量事件的衔接规则，过期事件或丢失增量不能永久污染显示状态。
- 操作必须区分已请求、已接受、已执行与结果已确认。超时或断线不自动等于操作失败。
- 取消等待、取消执行、关闭窗口、退出进程和停止后台任务的语义分别定义，并给出一致的用户反馈。

## 4. 持久化与副作用恢复

- 明确数据所有权、写入顺序、事务边界、迁移版本和恢复流程；根据存储后端保证说明进程崩溃、断电与主机故障的差异。
- 处理同一数据目录被重复打开的风险，明确单写入者或等效协调策略。
- 对可重放工作使用幂等键或去重记录；对文件写入、消息发送及远端操作，分别定义安全重试、结果核对和必要的人工确认路径。
- 外部副作用已发生而本地确认尚未落盘时，必须允许“结果未知”，不能盲目重做。无法撤销的效果不得被取消按钮虚假掩盖。
- 故障测试覆盖提交前后、工具执行前后、重启、断线与重连，验证恢复后状态和成果的一致性。

## 5. 安全边界必须真实

- 默认最小权限，明确工作区、文件、网络、进程、凭据与插件权限范围；高风险操作通过可审计的授权路径执行。
- [上游说明](../../README.md)明确 Pi 默认继承启动进程权限，不自带完整权限限制。客户端不能把接入运行时等同于已经实现安全沙箱。
- 进程隔离只能提供其实际具备的故障或资源边界。权限沙箱须有独立威胁模型、平台实现与越权测试；无法保证的限制应直接说明。
- 凭据使用合适的系统安全存储与最小暴露接口，不写入主题、普通配置、日志、崩溃报告或导出文件。
- 日志、诊断与遥测默认脱敏，明确采集内容、保存期限、导出与用户控制。诊断必须足以定位问题，但不能以可观测性为由泄露工作内容。
- 插件的来源、签名或完整性验证、权限声明、版本兼容、撤销和卸载行为需纳入设计与测试。

## 6. 测试验证行为与异常

- 单元测试验证核心规则；契约测试验证 IPC 与运行时边界；集成与端到端测试验证真实工作闭环。
- 重点覆盖授权拒绝、插件失败、存储错误、网络故障、取消、重启恢复、重复请求与结果未知，不只覆盖成功路径。
- Windows、macOS、Linux 都有明确的测试矩阵；分别覆盖路径、文件系统、进程生命周期、窗口、安装与更新差异。
- 用视觉与交互检查验证主题、字体、国际化、缩放、键盘、输入法和可访问性；截图通过不能代替行为正确。
- 测试数量和覆盖率只提供辅助信号，不能替代高风险场景的验证。依赖真实服务的测试需与确定性测试分离，明确成本与授权。
- 执行命令遵循根目录 AGENTS.md；未获允许的构建或测试不得为了“完成清单”擅自运行。

## 7. 性能先测量，再定预算

- 建立可复现的硬件、系统、数据规模与负载基线，再确定启动、内存、CPU、输入延迟、滚动和流式渲染预算。
- 测试真实长会话、大量日志、大文件或成果列表、多工作区与并发任务，包含持续运行后的资源增长。
- 控制事件频率、渲染量、队列、缓存和资源生命周期；根据测量采用增量更新、虚拟列表或背压等方案，不预设所有优化都必要。
- 输入、滚动、任务切换和流式输出互不明显阻塞。性能退化必须可检测、可复现、可定位。
- 不在未测量时承诺具体数字；最低硬件要求与性能预算是待评估项。

## 8. 发布、升级与完成标准

- 发布流程需验证构建产物、依赖来源、签名与平台适用的分发要求。更新需校验完整性，处理下载中断、安装失败与版本不兼容。
- 数据迁移必须测试成功与失败路径，设计备份和恢复策略；回退应用版本不等于数据可以直接回退，须明确支持边界。
- 变更完成时报告源码位置、测试或检查命令、实际结果、未运行项及原因、已知风险。必要时提供交互、性能或恢复证据。
- 生产发布以已验证的功能、可靠性、安全性和平台兼容性为准，不能靠文档声明、演示成功或一次启动通过认定就绪。
- 文档修改检查内容一致性、相对链接和空白错误；不将文档检查声称为客户端测试通过。
